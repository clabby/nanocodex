# Claude Code 2.1.284 interactive TTY probe (2026-09-28)

**Correction to earlier work:** this experiment ran the actual `claude` interactive terminal harness, not `claude -p`. The installed 2.1.284 CLI ran in a new tmux session on the authorized macOS Hand, in a synthetic isolated working directory. A second *interactive* window used `--permission-mode manual`. Its existing logged-in Claude Enterprise subscription performed its own authentication. A process-scoped HTTPS CONNECT/TLS relay kept the original `api.anthropic.com` host, was trusted only by those CLI processes, and captured structural request/response metadata. A fixed allowlist passed through public `rust-lang.org` TLS without decrypting page traffic. There are **no captured token/header values, cookies, user IDs, full prompt/response contents, or private page text** in [the compressed structural trace](nanoclaude-interactive-aggregate.jsonl.gz). The temporary CA/private keys and relay/CLI processes were removed/stopped afterward. The trace has SHA-256 `47756dd7bcc0ac3256e61eb5dc2039312c95223d71ceaf8a8dcc02b8073560e9`.

## Scope and counts

Fourteen synthetic turns in the default interactive auto mode, including Read, ToolSearch→WebSearch, AskUserQuestion with a selected option, `/plan`, an Agent handoff, `/compact`, Bash, Edit, WebFetch, and a missing-tool lookup. Two additional manual-mode turns tested Bash and an Edit approval. The relay recorded **53 rows:** 43 `/v1/messages` calls (35 main, 4 auxiliary, 3 subagent, 1 compaction); startup settings/policy/MCP reads (two each), one `/api/web/domain_info`, and three public page TLS tunnels. Every row was HTTP 200 except the two settings 404s and two policy 304s. Request-class labels are observed CLI header *values*, not headers a third-party client should copy. These prompts were not a benchmark or exhaustive proof of every conditional tool.

## Differences from `-p` that matter

- Before the first interactive main turn, an **auxiliary Haiku 4.5** Messages request generated a session title using a JSON-schema output format, three short system blocks, disabled thinking, no tools, max_tokens 32000. This auxiliary call was not the model's answer.
- The initial interactive main tool catalog contained **13 names**: `Agent`, `AskUserQuestion`, `Bash`, `Edit`, `ListAgents`, `Read`, `ReportFindings`, `ScheduleWakeup`, `Skill`, `ToolSearch`, `Workflow`, `DeferredToolPlaceholder`, `Write`. `WebSearch`, `WebFetch` and `ExitPlanMode` appeared after discovery/plan use; `Glob`/`Grep` were *not* available in this session (a direct `select:Glob` ToolSearch returned no match). Conditionality matters more than a universal static list. After discovery, tools remained loaded over turns and manual compaction.
- Main Opus 5.5 requests had four system text blocks (last two 1-hour cached), adaptive thinking `display:updates`, effort medium, `clear_thinking_20251015 keep:all`, diagnostics previous-message ID, `safeguards` (list), `speed` (string), and metadata keys. The first main request had three user text blocks followed by a **system-role message** carrying 22,756 characters with a 1-hour cache marker; later turns replayed prior messages and a short system-role cache block. These system-role messages are not representable in the current two-role Nanoclaude transcript. Do not copy private prompt content or first-party request-identity headers.
- `ToolSearch` was a **client** call: `query` and `max_results` were required in the observed schema. `select:WebSearch` returned a `tool_reference` in a user tool_result, then WebSearch appeared in the *next* main request. Selecting an unavailable tool returned a string no-match result. The CLI also appended a small text block to the ToolSearch result message.
- Client `WebSearch` made a separate **auxiliary Opus** Messages call, with only a short user query, three short system blocks, server `web_search_20250305`, `tool_choice:{type:auto}`, max_tokens 128000, effort medium, no main-history blocks. Its response included server_tool_use and web_search_tool_result; the original main loop resumed with a **string user tool_result**. The prototype had incorrectly forced `tool_choice:{type:tool}`.
- Client `WebFetch` followed a different path: a `/api/web/domain_info` request, **direct public HTTPS fetches** from the CLI (including redirects; raw page TLS passed through our allowlisted tunnel), then an **auxiliary Haiku 4.5** Messages request with fetched page content, no tools, disabled thinking, and a user prompt. The original main loop resumed with a string user tool_result. It did **not** make a nested Anthropic `web_fetch` server-tool request in this observed path. The first attempt failed because the relay deliberately denied non-Anthropic CONNECT; the second succeeded once public fixture hosts were allowlisted. A host-approved fetcher/redirect/domain policy is therefore required; simply adding `web_fetch_20250910` to the main request is not CLI parity.
- `AskUserQuestion` paused the terminal on a native Blue/Green selector and resumed only after a user selection; the next main request included its answer as a string tool_result. In manual mode, `Edit` paused on a diff approval; `Read`/`Bash(pwd)` did not. Permission UI is a harness responsibility, not just a JSON tool handler.
- `/plan` changed prompt packing (an additional 5,498-character system-role block), wrote a plan file under the CLI's own `~/.claude/plans`, discovered `ExitPlanMode`, and opened an execution-approval UI. We dismissed that UI without executing the plan. The discovered tool remained advertised after returning to auto mode.
- An `Agent` call spawned a distinct **subagent** request class with a separate three-block system prompt and a six-tool catalog: Bash, Read, Skill, ToolSearch, DeferredToolPlaceholder, SubagentHandback. Its result reached the parent asynchronously as a framed handback; the parent made additional main requests when the agent finished. A simple synchronous function-call loop cannot replicate this lifecycle.
- Interactive `/compact` made a separate ordinary Messages request with the full prior history, a two-block user compaction instruction (one 6,361-character text-only instruction), current client tools, and CLI request class `compaction`; no top-level `compaction` edit. The following main turn had **five messages**: a 4,244-character summary continuation user message, an empty system-role message, an assistant thinking/text message, a new multi-block user message, and a cached system-role message. The CLI recalled the chosen synthetic color after compaction. This differs from Nanoclaude's current one-user-message summary continuation. It does not prove the automatic trigger threshold in ordinary interactive use.

The trace lists block types, lengths, tool names/schema-property names, statuses, usage and timings only. It intentionally omits the CLI's private system prompt, result bodies, credential values, and account metadata. The `-p` measurements remain useful for that mode but **must not be substituted** for interactive behavior. No custom Nanoclaude subscription authentication has been exercised; the CLI used its own login.

## Implementation implications

1. Model a Claude **harness** above Messages with distinct main/auxiliary/subagent/compaction request classes, permission UI, asynchronous handbacks, dynamic tool catalog and independent public-web capabilities. Do not fold interactive behavior into the old `-p` approximation.
2. Match tested wire shapes (client ToolSearch, nested WebSearch auto choice, direct client WebFetch with host-approved fetch + auxiliary summarization, system-role context, cached blocks), while separating observed first-party-only fields from documented third-party API support.
3. Build a host-authorization and effect-receipt layer for every Claude-named tool before advertising it. The opt-in file/Bash/task adapters and search prototype are partial, not full Claude Code parity.
4. Obtain the trusted-program non-secret OAuth/client integration contract before using subscription traffic from Nanoclaude; observing Claude Code headers or a working session does not grant a third-party app that identity.
