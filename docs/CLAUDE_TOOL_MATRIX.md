# Claude-native tool implementation matrix (2026-09-28)

The Claude backend must **never advertise** `exec_command`, `apply_patch`, `web__run`, `exec`, `wait`, or Responses `tool_search` to Claude. `nanocodex-tools` may supply private host execution primitives behind an explicit Claude adapter and host permission policy; its OpenAI-visible definitions are not the Claude catalog. A tool is only advertised when its implementation, permission boundary and result encoder are available. This inventory tracks the current Claude Code tools reference, not a promise that every item is present in every CLI session/provider/platform.

| Family | Claude Code names | Current status / required implementation |
| --- | --- | --- |
| Files, process, search | `Bash`, `Read`, `Edit`, `Write`, `Glob`, `Grep`, `NotebookEdit`; conditional `PowerShell`, `Monitor`, `LSP` | **Partial, explicit opt-in:** `Read`, `Edit`, `Write`, `Glob`, and `Grep` have separate text-only handlers in `nanocodex-tools::ClaudeWorkspaceFiles` and a `ClaudeBuilder::workspace_files` adapter (`workspace-files` feature). Unlike full Claude Code: Grep supports content/files/count modes, context, case, output limits and simple glob; it rejects unsupported file type filters and complex glob syntax. Glob covers `*`, `?`, `**`; files are UTF-8, 1 MiB max; output is capped at 64 KiB. Host must authorize and OS-isolate the root; in-process path checks are not a security sandbox. `NotebookEdit` now has an opt-in bounded `.ipynb` editor; replacement/deletion requires explicit `cell_id`, and all paths require host isolation. `Bash` has a Claude-schema adapter but is advertised only with an explicitly injected `SandboxBashExecutor`; no ambient host shell is supplied, and background/sandbox-bypass modes are refused. `PowerShell`, `Monitor`, `LSP` remain **not implemented/advertised**. Native permission UX, PTY/background sessions, images/PDF reading, and full glob/type search parity remain outstanding. |
| Web | `WebSearch`, `WebFetch` | **Partial, explicit opt-in:** Claude Code client-side `WebSearch`/`WebFetch` have separate schemas and a bounded `ClaudeWeb` adapter backed only by a caller-injected `ApprovedWebProvider`; no default provider, network access, or end-to-end web execution exists. They are not aliases of `web__run`; Claude Code's fetch is prompt-directed, lossy and policy-scoped. Distinct Claude Platform server `web_search_20250305`/`web_fetch_20250910` may be enabled explicitly via `ServerToolDefinition`, executed by Anthropic; synthetic tests cover search results/citations and `pause_turn`, not live search. |

Do not assume MCP resource parity. |
| Orchestration | `Agent`, `AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`, `EnterWorktree`, `ExitWorktree`, `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`, `TaskOutput`, `TaskStop`, `TodoWrite`, `CronCreate`, `CronDelete`, `CronList`, `ScheduleWakeup`, `ListAgents`, `SendMessage`, `Workflow`, `SubagentHandback`, `EndConversation` | **Partial:** `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`, and `TodoWrite` have opt-in bounded, session-local handlers with cycle-checked dependencies; they are not durable or cross-agent. `Agent`, question/plan/worktree, output/stop, cron, messaging and workflows remain **not implemented/advertised** until authority and lifecycle contracts are wired. Do not substitute session-local tasks for durable account scheduling. |

Synthetic only: dynamic-filtering controls, beta MCP request plumbing, live billing and client implementations remain untested/unsupported. Explicit opt-in may incur separate provider charges. |
| User-defined functions | caller-provided Claude `ToolDefinition` | **Implemented** with assistant `tool_use` and single user `tool_result` message, ordered error results; optional parallel execution requires caller to attest independence. No Codex definitions are implicitly loaded. |

Safety design: Claude-visible registry and JSON schemas are independently versioned; translate into a private executor with `(session, turn, tool_use_id)` effect receipts, host approval and filesystem/network boundaries. Do not assume `WorkspaceToolRuntime::exec_command` is sandboxed: its shell accepts absolute workdirs and ignores model-supplied approval flags. Limit result bytes/media and preserve source citations. For side effects, cancellation or unknown outcome must not automatically re-execute the same call. Keep same-tool result blocks together, signed thinking and server result ciphertext unmodified. Native server tools are charged separately; opt-in only. No real subscription token or provider traffic was used in the synthetic tests.

## Controlled 2.1.284 CLI wire checks (fake-key loopback, no subscription traffic)

A non-bare interactive invocation exposed `AskUserQuestion`, `EnterPlanMode`, and `ExitPlanMode` in addition to the 20 tools of default `-p`; a forced-all `-p` fixture exposed 26. These sets are conditional, not a universal full registry. A non-first-party `ANTHROPIC_BASE_URL` disables tool search by default per the [official environment reference](https://code.claude.com/docs/en/env-vars). With `ENABLE_TOOL_SEARCH=true`, a print request instead exposed `ToolSearch` and `DeferredToolPlaceholder` among 12 initial tools. A synthetic `ToolSearch` call selected `WebSearch`; the next request advertised `WebSearch` and returned a user `tool_result` containing a `tool_reference`. This is a Claude Code **client** discovery flow, distinct from Anthropic's server tool-search API. At least 31 unique names were observed across these fixtures; that is not an exhaustive count.

With a synthetic long first assistant response, `--continue` performed a separate, ordinary Messages summarization request containing prior history and a text-only compaction instruction, then rebuilt the next request around the returned summary. It continued to advertise its three bare-mode tools even on the summarization request; no top-level API `compaction` parameter or `compact_20260112` edit appeared. A separate two-`Read` call test returned both matching results in one user message with the failed result marked `is_error:true`; result blocks arrived in completion order, not necessarily tool-use order. These are controlled wire observations, not evidence about live subscription billing or real-model decisions.

## Authenticated 2.1.284 subscription sample (synthetic prompts)

A process-local, credential-redacting TLS relay of the **actual logged-in CLI** (not a fake API-key fixture) measured 20 successful `-p` prompts plus a separate valid three-turn continuation and four long-context turns. No credential/header values or full content were retained. Real main requests used four system blocks with 1-hour ephemeral cache markers, adaptive thinking with `display:updates`, and `diagnostics.previous_message_id`; the earlier fake-key fixture's three-block system and `display:omitted` must not be treated as subscription parity. Subscription authentication was handled entirely by the installed CLI, not this backend.

Claude Code's `WebSearch` is a **client** tool, but servicing it triggered a **nested streamed Messages request** with Anthropic's `web_search_20250305` **server** tool. The CLI then fed the nested search's outcome back as a string user `tool_result` for its original client call. A deferred `ToolSearch` call exposed `WebSearch` in the next main request; two discovery workflows each called web search twice. This nested execution is missing from the current opt-in `ClaudeWeb` adapter, whose injected `ApprovedWebProvider` alone does not reproduce Claude Code behavior.

Two actual client-managed compactions were observed with `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000` and unusually long synthetic inputs. Each made an ordinary Messages request marked by the CLI's `x-claude-code-request-class: compaction`, carrying prior history and a text-only summary instruction; the same client tools remained advertised. The next `main` request used a continuation preamble and summary. Neither API `compaction` nor `compact_20260112` was sent. These observations do not establish default trigger frequency or confer authority to copy first-party identification headers into Nanoclaude; subscription transport requires its own approved integration.
